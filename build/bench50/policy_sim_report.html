Findings

1. Hot experts are not the same thing as a high hit rate — but not in the direction we expected

The working hypothesis going in was that individual-expert hotness undercounts experts that only matter as part of a repeating cluster, and that protecting those clusters would beat plain frequency ranking. That part of the hypothesis holds up: every single hotness-only or cluster-aware pinning policy tested — 33 configurations across four different formulas — scored below plain LRU. Pinning experts because they were hot in the past actively hurt hit rate on this workload, it didn't just fail to help.

The reason is workload shape, not formula quality. 50 prompts here are 50 genuinely different algorithms — quicksort, a trie, Dijkstra's algorithm, a hash map — with little routing overlap between them. A pin built from cumulative, all-time frequency is protecting yesterday's working set at the expense of today's. Plain LRU has no such bias: it reallocates the entire budget to whatever the current prompt actually needs within a few dozen tokens, which is exactly what a low-repetition workload rewards.

2. The gap that matters is LRU vs. the oracle, not LRU vs. the pin policies

Plain LRU (64.38%) sits 18.8 percentage points below the true achievable ceiling (83.19%). That gap is real and it's large — it means there is genuine exploitable structure in this trace that none of the 33 hotness/cluster/frequency policies tried here captured. The oracle wins by using future knowledge (it evicts whatever won't be needed again soonest); no online policy gets that for free. But it's the right target to chase: a policy that predicts near-future need — not past frequency — is the only kind of formula that can close this gap. That's what the N+1/N+2 cross-layer predictor from earlier in this session was already reaching for; it's a better-aimed idea than frequency-based pinning, this data just didn't test it in this simulator.

3. Simulator matches reality, so the ranking is trustworthy

The replica of the real C++ policy (pin top-17/layer, refresh every 5 prompts) scored 59.49% in simulation against 60.64% measured on the actual GPU run — a 1.15-point gap fully explained by approximating "every 5 prompts" with an average token count rather than exact prompt boundaries. That closeness is the validation: the simulator is a faithful stand-in for the real engine, so the full ranking above can be trusted, including the conclusion that the live policy is currently leaving hit rate on the table relative to doing nothing.

4. What to actually ship

Immediate, zero-risk change: drop the pin entirely and run plain LRU. It's simpler than what's live today (no periodic refresh, no core/mates bookkeeping) and it measured better on every metric in this trace. Longer-term, the 18.8-point oracle gap is the real target — closing it needs genuine lookahead (the cross-layer predictor), not a better historical-frequency formula, because this data shows historical frequency is actively counterproductive on a diverse workload.
